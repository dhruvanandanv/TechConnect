# TechConnect Technical Interview Preparation & Architecture Defense

This document provides a comprehensive technical interview guide, architectural defense rationales, and deep-dive question-and-answer scripts for **TechConnect — AI-Powered Enterprise IT Service Management Platform**.

---

## 1. Elevator Pitches

### "Explain TechConnect in 60 Seconds"
> "TechConnect is an enterprise-grade IT Service Management platform that unifies ticket lifecycle governance with automated SLA compliance and grounded AI intelligence. On the backend, we use Java 21 and Spring Boot with Spring Security and JWT for strict role-based access control across Employees, Engineers, Managers, and Admins. For data persistence, we architected a polyglot model: PostgreSQL manages ACID relational ticketing and SLA audit trails while hosting dense vector embeddings using pgvector, and MongoDB stores unstructured Knowledge Base documentation.
> What sets TechConnect apart is our Retrieval-Augmented Generation layer: rather than letting an LLM generate hallucinations or take unvetted actions, our Python FastAPI microservice extracts semantically similar SOPs using SentenceTransformers and pgvector HNSW indexing, generating verifiable, cited troubleshooting advice for employees and tri-fold grounded resolution proposals for engineers. Everything is containerized with multi-stage Docker builds, protected by sliding-window rate limiting, and built for production reliability."

### "Explain TechConnect in 3 Minutes"
> "In enterprise IT operations, organizations face two major pain points: first, SLA breaches and ticket backlogs caused by inefficient manual triage and siloed knowledge; second, the risk of unvetted AI tools hallucinating incorrect technical instructions or mutating operational data without authorization.
> TechConnect solves this through a hardened, full-stack microservice-adjacent architecture. 
> 
> At the presentation layer, a responsive React 19 SPA provides dedicated operational interfaces tailored to user roles. Employees create tickets and consult an AI Support Copilot; engineers triage queues, manage status lifecycles, and use an AI Resolution Assistant; managers monitor real-time SLA compliance, team workloads, and breach alerts.
> 
> The core business layer is built in Java 21 and Spring Boot 3.3. It implements a deterministic ticket state machine with SLA automation, calculating first-response and final resolution deadlines based on priority. The SLA clock dynamically pauses when a ticket transitions to `WAITING_FOR_USER` and automatically resumes with adjusted deadlines when the user responds. All endpoints enforce defense-in-depth security: BCrypt hashing, JWT authentication, Jakarta Servlet sliding-window rate limiting, and granular IDOR checks preventing unauthorized cross-user context leakage.
> 
> For data storage, we chose a polyglot persistence strategy. PostgreSQL guarantees ACID transactional integrity for tickets, audit logs, and SLA policies. Furthermore, we leverage the `pgvector` extension to store 384-dimensional dense vector embeddings generated by SentenceTransformers, indexed with Hierarchical Navigable Small World (HNSW) graphs for sub-millisecond cosine similarity searches. MongoDB is used for our Knowledge Base, managing polymorphic markdown documentation, author revisions, and atomic view and helpfulness metrics.
> 
> Finally, our AI intelligence layer runs as an independent Python FastAPI microservice. It provides two major capabilities: first, ML-based ticket categorization and priority inference; second, a 4-stage RAG pipeline. When a user asks a question, the system checks for prompt injection, executes semantic vector search in PostgreSQL, enforces a 4,000-character context budget, and synthesizes a grounded answer citing exact source SOPs. If similarity falls below 0.30, the AI safely refuses to answer rather than hallucinating. The entire platform is orchestratable via Docker Compose with non-root security and sanitized Actuator health probes."

## 2. Key Architectural Decisions ("Why Did You Choose...?")

### Q1: "Why did you choose Java Spring Boot for the core backend?"
**Answer**:
1. **Type Safety & Enterprise Maintainability**: Java 21 provides strong static typing, record classes, and virtual threads, making large-scale business logic (such as deterministic state machines and SLA calculation rules) robust and refactoring-safe.
2. **Spring Ecosystem Maturity**: Spring Boot 3.3 provides production-grade components out of the box: Spring Security 6 for stateless JWT authorization, Spring Data JPA / Hibernate for relational mapping, and Spring Boot Actuator for sanitized container health probes without needing custom boilerplate.
3. **Transaction Management**: Spring's declarative `@Transactional` boundaries guarantee ACID transactions across multi-table operations (e.g., ticket creation, status history logging, assignment audit logs, and SLA milestone recording).

### Q2: "Why did you choose a Polyglot Persistence model (PostgreSQL + MongoDB)?"
**Answer**:
Different data access patterns require different storage engines:
- **PostgreSQL**: Relational, tabular data with strict relational constraints and foreign keys. Tickets, users, roles, teams, departments, status transitions, comments, and SLA policies require ACID compliance. If an SLA deadline updates or a ticket status changes, it must be atomically committed with audit log consistency.
- **MongoDB**: The Knowledge Base contains polymorphic, semi-structured documents. Technical articles vary widely—they contain rich Markdown, variable tags, code blocks, version history, author metadata, and atomic feedback counters. Document databases excel at document-level retrieval without complex multi-table joins.
- **pgvector in PostgreSQL**: Rather than deploying a third, complex standalone vector database cluster (like Milvus or Pinecone), we utilized PostgreSQL's native `pgvector` extension. This keeps vector embeddings adjacent to relational data, simplifies backups, reduces operational overhead, and enables relational filtering combined with cosine vector search in a single transaction.

### Q3: "Why pgvector instead of a dedicated vector database like Pinecone or Chroma?"
**Answer**:
1. **Operational Simplicity**: Introducing a dedicated vector database requires managing another distributed cluster, network hops, separate authentication, backup schedules, and synchronization pipelines.
2. **ACID Consistency & Hybrid Queries**: With `pgvector`, vector chunks live directly inside PostgreSQL. We can perform hybrid queries combining SQL filters (`WHERE status = 'PUBLISHED'`) with vector cosine similarity (`<=>`) in a single query execution plan using HNSW indexing.
3. **Zero External SaaS Cost & Privacy**: Running pgvector locally in Docker eliminates external cloud API costs and ensures proprietary corporate troubleshooting documentation never leaves the organizational perimeter.

### Q4: "Why RAG instead of fine-tuning an LLM?"
**Answer**:
1. **Zero Hallucination Tolerance**: Fine-tuned models encode knowledge into internal weights probabilistically; they still hallucinate and cannot cite specific source lines. RAG operates by retrieving ground-truth documentation at runtime, constraining the LLM to synthesize answers exclusively from cited chunks.
2. **Instant Dynamic Updates**: In an enterprise, IT SOPs, VPN credentials, and policies change daily. Updating a RAG system requires merely updating or inserting a MongoDB article, chunking it, and saving its embedding in PostgreSQL (which takes 200ms). Updating a fine-tuned model requires gathering training data, running expensive GPU training, and redeploying weights.
3. **Auditability & Provenance**: RAG provides transparent, verifiable provenance. Every answer generated in TechConnect cites `[SOURCE N]` with the exact article ID, title, and similarity score.
4. **Access Control & RBAC**: In RAG, we can filter vector chunks based on the user's role before context construction. Employees only retrieve chunks from published SOPs, while engineers can retrieve draft SOPs and resolved ticket histories. A fine-tuned model cannot enforce runtime role-based data isolation.

### Q5: "How do you prevent hallucination in TechConnect?"
**Answer**:
We implement a multi-layered anti-hallucination defense:
1. **Strict Semantic Retrieval Quality Gate**: Before calling any generation model, we evaluate candidate chunk similarity scores. If no chunk meets our minimum threshold (`minSimilarity >= 0.30`), the LLM is **never invoked**. The system returns an immediate safe refusal: *"I could not find verified knowledge base articles on this topic."*
2. **Context Budget Capping**: Context Builder constructs strict provenance blocks with numbered source tags and enforces a hard budget cap (4,000 characters for Copilot, 6,000 characters for Resolution Assistant) to prevent prompt dilution and lost-in-the-middle attention degradation.
3. **Hardened System Prompt Grounding Invariants**: The system prompt explicitly instructs the LLM: *"You are a strict, grounded IT Support Synthesizer. You MUST answer using ONLY the facts explicitly stated in the provided SOURCES. Do not assume or extrapolate. If the sources do not provide the answer, state that clearly."*

### Q6: "How do you secure AI against prompt injection and malicious queries?"
**Answer**:
1. **Pre-Generation Regex Pattern Interception**: All incoming queries pass through a heuristic security filter (`prompt_builder.py`) scanning for malicious intent (e.g., attempts to extract credentials, bypass MFA, dump LSASS, or override system prompt instructions like `ignore previous instructions`).
2. **Prompt Boundary Delimiters**: System instructions, user queries, and retrieved context chunks are strictly separated with XML-like boundary tags (`<context>`, `<user_query>`, `<system_rules>`) so the model distinguishes instructions from data.
3. **Defense-in-Depth RBAC & IDOR**: The AI engine never accesses the database directly based on client parameters. Spring Boot evaluates `assertCanViewTicket` to verify the user owns or is assigned the ticket before passing its details to Python.
4. **Non-Autonomous Safety Invariant**: The AI Resolution Assistant is strictly advisory. It generates suggested text, but **never** calls mutating database APIs, changes ticket status, or resolves tickets autonomously. A human engineer must review and manually submit the resolution.

### Q7: "How does ticket authorization work (RBAC & IDOR)?"
**Answer**:
1. **Role-Based Access Control (RBAC)**:
   - Evaluated at controller and service layers via `@PreAuthorize`.
   - `ROLE_EMPLOYEE`: Can create tickets, view own created tickets (`/api/tickets/my`), add comments to own tickets, and access public knowledge articles.
   - `ROLE_ENGINEER`: Can view assigned tickets, claim unassigned tickets, update statuses, execute resolution assistant, and author knowledge articles.
   - `ROLE_MANAGER` & `ROLE_ADMIN`: Global visibility across all tickets, reassign tickets, manage SLAs, view executive analytics, and publish/archive knowledge articles.
2. **Insecure Direct Object Reference (IDOR) Defense**:
   - In `TicketServiceImpl.assertCanViewTicket(Ticket ticket, String userEmail)`:
     - If the caller is an Employee, the system verifies `ticket.getCreatedBy().getEmail().equals(userEmail)`. If it does not match, it throws `TicketAccessDeniedException` (HTTP 403 Forbidden).
     - If the caller is an Engineer, the system verifies the ticket is assigned to them, created by them, or currently open in their team queue.
     - This guarantees that knowing an integer ticket ID (e.g., `/api/tickets/42`) never allows an attacker to inspect another user's private ticket.

## 3. Core Technology Deep-Dive Q&A

### Java & Spring Boot
- **Q: What is the benefit of using Spring Data JPA Specifications?**  
  **A**: In `TicketSpecification.java`, we dynamically construct predicates using the Criteria API based on optional query parameters (status, priority, category, date range). This avoids vulnerable dynamic SQL concatenation and generates type-safe, optimized SQL queries.
- **Q: How does connection pooling work in TechConnect?**  
  **A**: We use HikariCP configured with optimal production parameters: `maximum-pool-size=20`, `minimum-idle=5`, `connection-timeout=20000ms`, `max-lifetime=1200000ms`. Connections are reused across servlet threads to eliminate TCP handshake latency.

### Spring Security & JWT
- **Q: How are JWTs validated statelessly on every request?**  
  **A**: `JwtAuthenticationFilter` intercepts incoming requests, extracts the `Authorization: Bearer <token>` header, verifies the cryptographic signature using HMAC-SHA256 and the server's private secret, checks that `exp` is in the future, and loads the user authorities into the `SecurityContextHolder`.

### Python, FastAPI & Machine Learning
- **Q: Why FastAPI for the AI microservice?**  
  **A**: FastAPI offers high-performance asynchronous request handling (ASGI), native Pydantic data validation with automatic OpenAPI documentation, and minimal overhead for serving machine learning models in Python.
- **Q: How does the embedding pipeline work?**  
  **A**: We use `sentence-transformers/all-MiniLM-L6-v2`. It maps sentences and paragraphs into a 384-dimensional dense vector space. Chunks are normalized (code blocks and excess whitespace removed, sliding window of 300 words with 50-word overlap) before encoding. Embeddings are L2-normalized so cosine similarity equals the dot product.

### Docker & Production Deployment
- **Q: How does Docker Compose ensure services start in the correct order?**  
  **A**: We utilize `depends_on` with `condition: service_healthy`. The Spring Boot backend container will not start until PostgreSQL, MongoDB, and the FastAPI AI service have passed their respective health checks (`pg_isready`, `mongosh ping`, and `/health`).
- **Q: How are non-root users configured in Docker?**  
  **A**: In `backend/Dockerfile`, we create a group and user `spring` (UID 1001), grant ownership of `/app`, and declare `USER spring:spring`. This ensures that even if an arbitrary code execution vulnerability exists in an application library, the process cannot modify system configuration or break out of the container.
